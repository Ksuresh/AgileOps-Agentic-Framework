# Study 9: Cross-domain governance against an outcome-based oracle (frozen before any outcome measurement)

## Question
A Project Manager cannot judge DevOps, SRE, FinOps and security evidence alone, and each domain specialist sees only
their own domain. AAF claims that encoding cross-domain arbitration in deterministic rules, with bounded LLM investigation
where the rules lack evidence, chooses better governance actions than (a) siloed single-domain deciders, (b) an LLM that
decides from all raw evidence, and (c) simple fixed policies. Earlier studies scored actions against answer keys written by
the authors (or AI-assisted labels). Here **no one writes the answer key**: every candidate action is applied to the live
system and its measured consequences decide which actions were correct.

## Testbed
Google Online Boutique (pinned commit `b9a978db`) on a kind cluster in GitHub Actions; the built-in load generator is
removed; load is generated by the runner through a NodePort. Decisions concern the `frontend` deployment (Recreate
strategy, so a broken release cannot hide behind an old pod). metrics-server provides CPU use; trivy (v0.56.2) scans images.

## Cases (`cases.yaml`, 32)
2 controls, 12 single-domain faults, 18 compound faults, composed from: a feature release, a performance-regressed release
(CPU budget 40m/25m), a release that cannot start, a vulnerable image (A/B), a secret-like value in runtime configuration,
overload (100/160 clients on one replica), and over-provisioning (5/8 replicas at 4 clients); vulnerable images are also
placed in the stable release (so rollback cannot fix them). No case names a correct action.

## Calibration (healthy states only, before any action is measured)
`calibrate.py`: three healthy measurements (stable release, 1 replica, 20 clients, 45 s) and selection of vulnerable images
A and B by a fixed rule: candidate Online Boutique frontend tags newest first; keep tags that pull, roll out, serve HTTP 200
with the stable configuration, and carry at least one critical CVE more than the stable image; A = first, B = second.

Calibration result (`calibration/calibration.json`, run before any action was measured): stable image
`frontend:v0.10.6` (0 critical CVEs); healthy p95 699, 403, 408 ms (median 408 ms, so the reliability threshold is
816 ms); error rate 0%; vulnerable image A = `frontend:v0.8.0`, B = `frontend:v0.7.0` (gcr.io; 6 critical CVEs each).
(Artifact Registry tags could not be scanned and were skipped by the rule.)

## Actions and their implementation (fixed)
Applied to a freshly rebuilt incident state each time:
- Rollback to stable deployment / Block release and fix pipeline: restore the previous release's pod template (the second
  also blocks delivery; the measured state is the same).
- Patch or block release: keep the current release but replace a vulnerable image with the stable image and remove
  secret-like configuration (the feature stays).
- Mitigate and monitor: raise CPU/memory requests and limits (200m/500m CPU) and restart.
- Scale adjustment: HPA rule on the incident measurement, replicas = ceil(r * utilisation / 0.6), bounded to 1..6.
- No action (observe), Review scaling policy, Escalate for evidence/human review: no immediate change.

## Outcome measurement
For the incident and for each action: 45 s of HTTP load at the case's level (p95 latency, error rate), CPU per pod,
container restarts, running image (critical CVEs by trivy), secret-like configuration (regex
`(?i)(secret|passw|token|api[_-]?key)` on environment values), CPU footprint (replicas x CPU request), and whether the
feature is delivered. Each case is measured in two independent replicates on separate runners; metrics are averaged.

## Domain violations after an action (thresholds fixed now; numeric values from calibration)
- Reliability: p95 > 2 x healthy median p95, or error rate > 1%.
- Security: critical CVEs above the stable image's, or secret-like configuration present.
- Cost: CPU footprint > 3 x the healthy footprint (300m).
Delivery (feature still deployed) is recorded separately and used only as the secondary tie-break below.

## Oracle
- **Primary (O1):** an action is correct if its measured outcome has the minimum number of violated domains among all
  actions for that case (ties: all tied actions are correct).
- **Secondary (O2):** among O1-correct actions, prefer those that keep the feature delivered, then the lower footprint.
- **Tertiary (O3):** Pareto: an action is admissible if no other action is at least as good in every domain and better in one.

## Deciders (all see only the incident snapshot; none sees outcomes)
- AAF (deterministic assessment and arbitration, unchanged code, plus selective bounded investigation; LLM = Qwen3-8B
  via Ollama), B1 deterministic-only, B2 rule-based retrieval, B3 always-on agents with deterministic authority,
  B5 Agentic-only (LLM decides), B6 policy-aware Agentic-only (LLM decides, with AAF's rules in its prompt, thinking on).
- Siloed experts: the same deterministic rules given only one domain's evidence (D-DevOps, D-SRE, D-FinOps, D-Sec), and
  the LLM domain agents' own proposals (L-DevOps, L-SRE, L-FinOps, L-Sec).
- Fixed policies: dominant-domain baseline; always rollback; always no action.
- Evidence mapping (fixed, mechanical): sre = p95, error rate, availability (HTTP), saturation (CPU/limit); deploy =
  restart loops (container restarts), config drift (secret-like configuration, as in the earlier Online Boutique study);
  finops = CPU-request change vs. healthy footprint (proxy); sec = new critical CVEs, policy violation.
- AAF's code and thresholds are not changed for this study (file hashes recorded by the workflow).
- Deciders use the replicate-1 snapshot of each case; outcomes are averaged over both replicates. B2 uses the frozen
  field-to-tool map of Study 6, extended with `deploy.restart_loops -> get_restart_history` (same tool family).
- Implementation: `decide.py` (deciders; never reads outcomes), `analyze.py` (oracle and tests).

## Study 9b: withheld evidence
For each case with a vulnerable image, secret-like configuration, a non-starting release, or a reliability fault, a
variant withholds the decisive measurement from the snapshot (status `missing`) and makes it available through the
matching read-only tool (`get_vulnerability_details`, `get_policy_gate_status`, `get_restart_history`,
`get_latency_history`), whose result is the live measurement. Oracle unchanged.

## Hypotheses and tests (fixed now)
- **H9.1 (primary):** on the 18 compound cases (O1), AAF is correct more often than each siloed expert (8 comparisons).
- **H9.2:** on all 30 fault cases (O1), AAF vs. B5, B6, dominant-domain, always-rollback.
- **H9.3 (9b):** on withheld-evidence variants (O1), AAF vs. B1 (benefit of investigation), and AAF vs. B2 and B3.
- **H9.4:** controls: proportion of deciders choosing an action with zero violations and no change (no false alarm).
- Tests: exact McNemar on paired per-case correctness, Holm-adjusted within each hypothesis. O2 and O3 reported as
  secondary. LLM arms run 3 times; majority action per case. AAF can lose any comparison; all results are reported.
