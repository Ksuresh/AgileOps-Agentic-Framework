# AAF Experimental Protocol — Post-Review 2026

## 1. Purpose

This protocol preserves the existing AgileOps Agentic Framework (AAF) and redesigns the evaluation around the paper's actual claim: project managers making Agile/DevOps release decisions face fragmented operational evidence distributed across DevOps, SRE, FinOps and DevSecOps sources. AAF is intended to coordinate that evidence into an evidence-bounded governance recommendation and expose the decision through a grounded natural-language interface.

The experiment therefore does **not** optimize for generic classification accuracy. It tests whether cross-domain coordination adds governance value in the conditions for which AAF was designed.

All scenario definitions, intervention oracles, thresholds and evaluation rules must be frozen before execution. Results must not be retroactively relabelled or tuned to improve AAF scores.

## 2. Research Questions

- **RQ1 — Cross-domain governance value:** Does AAF improve release-governance decisions when the decision depends on evidence from two or more operational domains, compared with simpler single-domain/dominant-domain approaches?
- **RQ2 — Safety under healthy or incomplete evidence:** Does AAF reduce false interventions and appropriately abstain or escalate when evidence is healthy, missing, partial or contradictory?
- **RQ3 — Evidence-grounded PM interaction:** Does the LLM explanation/interface preserve the underlying governance decision and evidence while making the result understandable and queryable by a project manager?
- **RQ4 — Realistic operational validity:** Can AAF operate on telemetry generated by open, realistic microservice workloads and on public operational datasets, rather than only designer-generated scenarios?

## 3. Existing Assets Retained

### 3.1 Existing controlled 30-scenario benchmark

The existing scenario generator remains a **broad stress-test/control benchmark**. It already contains DevOps, SRE, FinOps and DevSecOps scenarios and several secondary-domain effects. It is retained for backward comparability, but aggregate accuracy from this benchmark will not be treated as the sole efficacy claim.

Each existing TC case will be tagged before rerun as one of:

1. single-domain control
2. cross-domain/compound
3. conflicting-objective
4. incomplete/noisy evidence
5. healthy/abstention control

The existing 30 scenarios will not be deleted or relabelled after observing results.

### 3.2 Existing runtime intervention suite

The existing RT-01 through RT-20 intervention catalogue is retained. It already covers:

- healthy baseline
- service stops
- restart/deployment failures
- CPU/memory constraints
- scale-out/over-provisioning
- high load
- SRE + FinOps compound conditions
- DevOps + SRE compound conditions
- DevSecOps single-domain and compound conditions
- missing/noisy evidence variants

The current intervention oracles remain frozen unless a case is found to be technically impossible to execute as specified; any such case must be marked unsupported, not silently redefined.

## 4. Experimental Structure

### Study A — Existing 30-case controlled stress-test

Purpose: continuity with the existing manuscript and broad regression coverage.

Report:
- domain attribution accuracy
- admissible-action accuracy
- macro-F1 where class counts permit
- false intervention rate
- abstention/escalation rate
- Wilson confidence intervals
- paired comparison against dominant-domain baseline
- ablations: no-consensus, no-RER, no-utility, no-abstention where methodologically valid

Primary interpretation: background/stress-test, not the strongest novelty proof.

### Study B — Stratified cross-domain benchmark

Purpose: directly test AAF's claimed advantage.

Construct only the **minimum additional cases** needed after auditing the existing 30. Target final balanced coverage of approximately:

- 12–15 single-domain controls
- 18–24 cross-domain/compound release-governance cases
- 10–12 conflicting-objective cases
- 8–10 incomplete/noisy-evidence cases
- 8–10 healthy/no-action controls

Expected total: approximately 55–70 base cases including the existing 30.

Each case should define:
- observable evidence only
- domain(s) materially implicated
- admissible PM-level actions (set, not a single fragile label when multiple actions are defensible)
- release-governance rationale
- evidence sufficiency class
- whether abstention/escalation is admissible

Run each case under pre-specified deterministic evidence variants/noise seeds to produce at least ~250 evaluations.

Primary hypothesis: AAF may be similar to a simple baseline on single-domain controls, but should show a measurable advantage on cross-domain/conflicting subsets.

### Study C — Sock Shop runtime study

Purpose: realistic end-to-end evidence generation using an executable microservice workload.

Use the existing RT catalogue. Phase C1 should execute all technically supported cases RT-01–RT-20 with **at least 5 repetitions** per case where runtime cost permits. Cases that require evidence sources not yet collected must be marked unsupported until a real collector exists; do not fabricate security or billing telemetry.

Priority cases:
- RT-01 healthy baseline
- RT-02/03 service loss
- RT-04 restart/deployment instability
- RT-07/08 resource constraints
- RT-09/10 over-scaling/FinOps proxy
- RT-11 load pressure
- RT-12 SRE + FinOps compound
- RT-13 DevOps + SRE compound
- RT-17 DevSecOps + SRE compound, only if real security evidence is collected
- RT-18 DevOps + DevSecOps compound, only if real security evidence is collected
- RT-19/20 missing/noisy evidence safety tests

Collect and preserve raw runtime artifacts before inference.

### Study D — Google Online Boutique confirmatory runtime study

Purpose: second-workload external validity.

Online Boutique is a public cloud-first e-commerce microservice application with 11 services and a continuous load generator. It can run on Kubernetes clusters, including local/non-GKE environments. Reproduce a compact confirmatory subset of the same intervention classes used in Sock Shop:

- healthy
- service unavailable
- CPU/resource pressure
- over-scaling
- high load
- one SRE + FinOps compound case
- one DevOps + SRE compound case
- one incomplete-evidence case

Target: 8 intervention classes x 4–5 repetitions = 32–40 runs.

Do not claim this is production customer data. Describe it as a realistic open-source microservice workload used for controlled runtime validation.

### Study E — Public operational dataset validation

Purpose: address reviewer concern that all evidence is synthetic/testbed-generated.

Preferred external dataset: **AIOps Challenge 2020** because it contains operational metrics/traces and labeled failures from a production distributed-system context and has been used for RCA evaluation. Use only evidence fields that can be mapped without inventing unavailable DevOps/FinOps/DevSecOps signals.

Evaluation role:
- external validation of the SRE/operational-evidence path
- evidence ingestion and failure-domain localization under an independent dataset
- not a full four-domain AAF test if the source lacks cost/security/release metadata

Optional supplementary dataset: **GAIA / MicroSS**, which contains large-scale metrics, logs and trace data with recorded anomaly injections. This is useful for multimodal operational robustness but should be described accurately as a controlled/simulated operational dataset rather than production customer data.

Do not force public datasets into unsupported AAF domains.

### Study F — PM explanation and interaction study

Purpose: prove the second major contribution of the paper.

Compare three information conditions for the same frozen governance cases:

1. raw operational evidence/dashboard-style summary
2. structured AAF governance output without LLM explanation
3. grounded natural-language AAF explanation/interface

Evaluate:
- decision fidelity: explanation preserves domain/action selected by AAF
- evidence coverage
- unsupported-claim rate
- answerability of PM questions such as "Can I release?", "Why?", "What is blocking?", "What evidence supports this?", "Why not rollback?"
- comprehension/task accuracy using a pre-defined rubric
- response time/reading burden if human participants are used

If human participants are impractical, retain automated evidence-fidelity metrics and present human usability as future work rather than fabricate evaluator data.

## 5. Baselines

Mandatory baselines:

1. dominant-domain deterministic baseline
2. independent domain agents without cross-domain coordination
3. AAF without consensus
4. AAF without RER
5. AAF without utility layer
6. AAF without abstention/materiality gate (safety ablation)

Recommended additional baseline if reproducible:

7. single-LLM governance baseline supplied with the same frozen evidence snapshot. Its prompt, model/version, temperature and output schema must be fixed before evaluation.

## 6. Primary Metrics

### Decision quality
- domain attribution accuracy / macro-F1
- admissible-action accuracy
- exact action accuracy as secondary metric
- cross-domain subset accuracy
- conflicting-evidence subset accuracy

### Governance safety
- false intervention rate on healthy cases
- unsafe abstention rate on material incidents
- correct abstention rate
- correct escalation rate
- unsupported autonomous-decision rate

### Evidence integrity
- provenance completeness
- evidence coverage
- unsupported-claim rate
- RER trigger, accept and escalation rates

### Statistical reporting
- Wilson 95% confidence intervals for proportions
- paired McNemar test for paired categorical decisions
- effect size / absolute percentage-point difference
- bootstrap CI where appropriate for explanation/comprehension measures
- sensitivity analysis for tau, lambda, delta and utility weights, without post-hoc retuning

## 7. Interpretation Rules

- Do not claim AAF must outperform all baselines on single-domain cases.
- The central efficacy claim is supported if AAF shows a meaningful and statistically defensible advantage specifically on cross-domain/conflicting governance cases while preserving safety on healthy/incomplete cases.
- RER is evaluated primarily as an evidence-sufficiency/safe-escalation mechanism unless data independently demonstrates an accuracy benefit.
- LLMs are evaluated as a grounded explanation/interaction layer; they must not silently create operational facts or replace the deterministic governance evidence path.
- Testbed data (Sock Shop, Online Boutique) must be called realistic controlled runtime data, not customer production data.
- Public production-origin datasets must be described according to their published provenance and licensing.

## 8. Execution Order

1. Audit/tag existing TC-01–TC-30.
2. Build only missing controlled cases needed for balanced cross-domain/conflict/abstention coverage.
3. Freeze all controlled-case oracles and metrics.
4. Expand Sock Shop from the validated mini-pilot to all technically supported RT cases.
5. Add Online Boutique confirmatory runtime subset.
6. Add AIOps Challenge 2020 external operational-data validation.
7. Run baselines, ablations, sensitivity and statistical tests.
8. Run/finalize PM explanation evaluation.
9. Freeze artifacts/results before manuscript rewriting.

## 9. Paper-level claim to test

> AAF provides a PM-facing governance layer over fragmented Agile/DevOps operational evidence by coordinating DevOps, SRE, FinOps and DevSecOps signals into evidence-bounded release recommendations, with explicit abstention/escalation under insufficient evidence and a grounded natural-language interface for explanation and interaction.
